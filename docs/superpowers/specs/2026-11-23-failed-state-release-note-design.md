# Release note for the failed review state

## Goal

Tell users, in the README and the next release notes, that factory and factoryd v0.4.0 and older cannot read a board that holds the review state `"failed"`, and how to roll back safely.

## Overview

Ticket #150 asks for a release-notes line from the follow-ups of #118. `ReviewState::Failed`, written as `"failed"`, shipped in v0.5.0 (commit `de1f93f`, in tags v0.5.0 and v0.5.1). The v0.4.0 enum has only `Pending`, `Running`, `Pass`, `Changes` and `Skipped` and no `#[serde(other)]` fallback, so `Board::load` in v0.4.0 and older fails on the whole board as soon as one job holds `"failed"`.

The ticket says "older than this change". That is not exact: v0.5.0 and v0.5.1 read `"failed"`. What changed after v0.5.1 is the `Unknown` fallback (commit `5e5b80a`), which makes future unknown states degrade instead of breaking the board. The note must state both facts.

The release notes are generated by git-cliff from commit subjects (`cliff.toml`), so a hand-written note lives in README "Upgrading" and `docs/operations/releasing.md` tells the release maker to paste it into the draft, as it already does for "Check coverage".

### 1. README subsection

Add `#### Review states` right after the `#### Check coverage` subsection, ending before `### Refreshing seeded presets`. Its text, which the builder may reword lightly while keeping every pinned phrase of the Testing section:

> A reviewer run that fails or stalls before it gives a verdict is stored as the review state `"failed"` and shows as `failed` in `factory status`, for example `code:failed`. v0.5.0 added this state. `factory` and `factoryd` v0.4.0 and older cannot read a board that holds `"failed"`: they stop on the whole board, not just that job.
>
> From the release after v0.5.1, a review state the binary does not know loads as `unknown` and counts as no verdict, so a state added later no longer breaks the board.
>
> An older binary already stops on a home whose `<home>/VERSION` marker is newer. The board error shows only after that marker is deleted, or in a `factoryd` that still runs the old build, so restart `factoryd` after an upgrade.
>
> Before you roll back past v0.5.0, retry or rework every job that shows `failed` until its review gives a verdict. A job that was cancelled or merged while it still showed `failed` keeps that state, and the board stays unreadable for v0.4.0 and older, so do not roll back past v0.5.0 then.

### 2. Release step

In `docs/operations/releasing.md`, add one line right after the "Check coverage" paste line:

> In the first release after v0.5.1, also paste the "Review states" note from `README.md` (Upgrading) into the draft release.

The existing line "The changelog skips `chore:` commits, so this note is not generated." stays where it is.

## Error handling and edge cases

| Case | Behaviour |
|---|---|
| Rollback to v0.5.0 or v0.5.1 | reads `"failed"`; the note says the limit is v0.4.0 and older |
| Rollback to v0.4.0 with the marker in place | the version check stops it first; the note says so |
| A cancelled job holds `"failed"` | the note says it keeps the state and not to roll back past v0.5.0 |
| A state added after this release, read by v0.5.x | still breaks v0.5.x; the note only promises the fallback from the release after v0.5.1 |
| Dashboard | reads review states as strings, not affected; the note does not mention it |
| Later releases | the paste line names the first release after v0.5.1 only |

## Acceptance criteria

- `README.md` has a `#### Review states` subsection under `### Upgrading`, after `#### Check coverage`.
- The subsection says `"failed"` arrived in v0.5.0 and that v0.4.0 and older stop on such a board.
- The subsection says review states unknown to the binary load as `unknown` from the release after v0.5.1.
- The subsection names the `<home>/VERSION` check and says to restart `factoryd` after an upgrade.
- The subsection tells the user to retry or rework every `failed` job before rolling back past v0.5.0, and not to roll back when a cancelled or merged job still shows `failed`.
- No doc suggests editing `board.json` by hand.
- `docs/operations/releasing.md` tells the release maker to paste the "Review states" note into the first release after v0.5.1.
- `readme_documents_the_failed_review_state` and `releasing_doc_pastes_the_review_states_note` pass, and `cargo test -j4 -p factory-cli --test agent_lint` passes.

## Out of scope

- Teaching v0.4.0 to read the board. Old releases are not patched.
- A general rollback guide.

## Decisions

- Where does the note live? Options: a README Upgrading subsection plus a paste line in releasing.md, a releasing.md checklist line only, a new docs/release-notes/next.md file. Chosen: a `#### Review states` subsection under README Upgrading plus a paste line in `docs/operations/releasing.md`. Decided by: user
- What does the note tell a user who must roll back? Options: facts plus retry or rework every job that shows `failed` until its review gives a verdict and do not roll back past v0.5.0 while a cancelled or merged job still shows `failed`; facts plus "do not roll back past v0.5.0" only; facts plus a hand edit of board.json as a last resort; facts only. Chosen: facts plus retry or rework, with no board.json hand edit. Decided by: user
- How is the note pinned? Options: two `require_all` tests on key phrases in `agent_lint.rs`, an exact-text test, no test. Chosen: two `require_all` tests on key phrases. Decided by: user
- Does the note mention the version marker? Options: name the `<home>/VERSION` check and the factoryd restart, leave it out. Chosen: name it, since it decides when the board error can show at all. Decided by: call
- Does the paste line apply to every release? Options: the first release after v0.5.1 only, every release. Chosen: the first release after v0.5.1 only. Decided by: call
- Approach. Options: README subsection plus paste line, a commit body that git-cliff picks up, a new release-notes file. Chosen: README subsection plus paste line, the only one that follows the existing "Check coverage" pattern. Decided by: call
