# Factory improvement roadmap (2026-10-18)

Primary research for four items. Each item is a separate brainstorm, spec and plan series, started one at a time. Research was done by read-only agents and is a lead, not proof: re-verify against source before designing.

## Recommended order

1. Item 4, cache use. Cheapest, measurable, mostly prompt order and flags.
2. Item 3, small-job path. Reuses the item 4 findings (message and committer runs).
3. Item 1, learning loop. Needs job data to accumulate, so it gains most if started after 3.
4. Item 2, Agent Teams. Closed: not feasible (see below). Revisit only if Claude Code adds headless teams.

## Item 4: use more cache, create fewer new tokens

Findings:
- No cache setting exists in the factory. Default 5 minute TTL, no 1h setting (`ENABLE_PROMPT_CACHING_1H` is unused).
- Flags are built in `crates/factory-agent/src/spec.rs:83-116`. Resume (`--resume`) is used only for fix-round builders and committer or message retries. Per-task builders, the reviewer and fresh committers are cold starts (27 of 30 builder runs fresh).
- Prompt order is cache-unfriendly: volatile text (branch, shas, task excerpt, diff, round) comes before the long fixed rules, in the builder (`specs.rs` ~170-190) and reviewer prompts. The fixed text should come first.
- Each role has a different tool set, model and agent file, so cross-role cache sharing is not possible. The Claude Code system prompt also carries cwd, git status and date.
- Weighted formula is `input + cache_creation + output + cache_read/10` (`factory-core/src/budget.rs:8-13`). It has no 1.25x write premium, so it understates the cost of cold starts.
- Measured (58 usage lines in `~/.factory/projects/*/state/jobs/*/usage.jsonl`), average per run:

| Role | Runs | cache_creation | cache_read | Creation share |
|---|---|---|---|---|
| builder, fresh | 27 | 43K | 395K | 10% |
| builder, resumed | 3 | 38K | 129K | 23% |
| committer, fresh | 10 | 41K | 78K | 34% |
| reviewer | 8 | 29K | 36K | 45% |
| message | 9 | 18.5K | 1.2K | 94% |

Candidate work:
- Reorder prompts so stable text leads.
- Try the 1h cache TTL for runs that wait on checks and reviews.
- Measure gaps between builder, checks, reviewer and fix rounds against the 5 minute TTL (unmeasured, an inference only).
- Cut or merge the message agent (94% creation) and the committer.
- Consider resume across tasks within one plan.
- Add a write premium to the weighted formula, or report cost in USD.

Cache price multiples (plain API, from the claude-api skill docs): uncached input 1x, 5 minute write 1.25x, 1 hour write 2x, read about 0.1x. The 5 minute cache breaks even after 2 requests (1.35x against 2x). The 1 hour cache needs 3 (2.2x against 3x). It only pays when calls sharing a prefix start 5 to 60 minutes apart, so the gap timing from real jobs decides it.

1h TTL decision (2026-10-18): do not enable it on current data.
- Data: 58 usage rows, 11 jobs, only 4 resumed runs, so the sample is too small to trust. 39 of 47 consecutive run pairs were under 5 minutes apart. Net effect of 1h: +0.8% best case, -4.2% when earlier runs in the chain also pay the write premium, about -36% if it can only be set globally. One 48.6 minute gap carried most of the gross saving.
- In-run gaps: median 3.3 s, p90 27 s. 16 of 2,072 gaps (0.8%) in 11 of 227 runs were over 5 minutes, nearly all builders waiting on `cargo test` or `cargo bench` (up to about 10 minutes). The reviewer to next committer wait has a median of about 6.5 minutes.
- How to enable if revisited: `CLAUDE_CODE_PROMPT_CACHE_TTL=1h` (main conversation, v2.1.242+), `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL=1h` (subagents), or `ENABLE_PROMPT_CACHING_1H=1` (no stated minimum version). `FORCE_PROMPT_CACHING_5M=1` forces 5m. Verify with `claude -p "hello" --output-format json` and read `usage.cache_creation.ephemeral_1h_input_tokens`. Docs: https://code.claude.com/docs/en/prompt-caching.md
- CORRECTION, measured 2026-10-18: headless `claude -p` on this machine is already on the 1h cache. `claude -p "hello" --append-system-prompt "nonce <ts>"` wrote 25,032 tokens, all in `ephemeral_1h_input_tokens`, 0 in 5m, cost $0.1007 (a 2x write at $2 per MTok). So the "do not enable 1h" decision above is moot: it is on. The real question is the reverse: should one-shot roles that never resume (fresh committer, message, reviewer, and builders with no fix round) be forced to 5m with `CLAUDE_CODE_PROMPT_CACHE_TTL=5m` per run, to stop paying the 2x write? The gap analysis above suggests the extra 0.75x premium on all creation tokens is the cost already being paid (the "global switch" row, up to about 36% of weighted cost, though weighted cost counts a write as 1.0, so the dollar effect is smaller). Not yet decided. Caveats: one test run on a plain `claude -p` (the factory's `--agent` runs were not checked), and billing mode (subscription versus list price) is unknown, so dollar impact is unproven. A resumed run after 48.6 minutes still rewrote 109k tokens, which does not fit a live 1h cache, so something else (eviction, a different bucket) is also at work.
- DONE, 2026-10-19: the 5m and 1h split is logged in `usage.jsonl` as `cache_creation_1h`. The decision is a global `cache_ttl = "5m"` (the default for new projects). A per-role TTL is parked until more resumed-run data exists, see GitHub issue #3.
- Report, 2026-10-20: `factory tokens --cache [--days N]` shows cache use per role and resumed runs with gap and rewrite flag, to decide #3. Revisit when: enough runs log `cache_creation_1h`, resumed builders idle over 5 minutes rewrite the cache more than once, and the 49-minute miss in rocket job 023 is explained.
- Docs do not say whether `--agent` runs count as main conversation, or how plan limits weight cache writes.
- The system prompt embeds the working directory and git snapshot, so per-job worktrees probably make each job a cold start even for the same role.
- Better levers than 1h: prompt order, fewer cold-start runs, and splitting long test commands in builders.

Open questions: does `claude -p` honour a 1h TTL setting in the installed version, and does reordering change anything while the system prompt prefix differs per worktree?

## Item 3: affordable small bugs and enhancements

Findings:
- No lightweight mode. `.claude/commands/factory.md` and `crates/factory-core/assets/global-command.md` (lines 57-70) say there is no quick-task path, and force the full interview, spec, builder check and plan.
- That interactive cost is not shown by `factory tokens`, and is probably the largest part for a small job.
- Partial path: `factory new <slug> '<feature>'` without `--plans` (`commands.rs` 264-282). It makes one job at `build` with no spec check, and `plan.md` is placed by hand. A plan with no `### Task N` lines is a legacy single-builder plan. Not run, so what the reviewer gets as spec is unverified.
- Agent runs per job: builder, committer (one for the batch), reviewer per round, message agent for merge, sync message if main moved. Only the KB refresh (`kb_path` unset) and tickets (`tickets_on_merge=false`) can be switched off now. No switch exists for the reviewer, committer or message agent.
- Config-only cuts: `fix_rounds`, `commit_budget_weighted`, `commit_subagents=false`, `reviewer_model` and `commit_model` set to haiku, `budget_weighted`.
- Measured data is thin: one-task smoke run about 72K weighted, three-task toy plan about 73.5K. No split by role. Old subagent-driven jobs showed the `1-git-commit` skill running several 40-50K subagents.

Candidate work, by leverage:
1. A documented quick path in `/factory` and `factory new`: short interview, one combined spec and plan, no builder check. The reviewer needs a spec fallback.
2. A `--light` option or config key: use the existing git2 fallback `chore:` commit and the fixed merge and sync messages, so up to 3 agent runs are skipped.
3. Cheaper or skipped review for small, low-risk diffs (risky diffs must still go to a human).

Open questions: what counts as "small" (diff lines, task count, risk paths), and who decides, the user or the driver?

## Item 1: the factory learns from every spec and plan execution

Goal: specs and plans that run with little or no rework or bugs.

Findings:
- No learning mechanism exists. The KB refresh checks code facts only. It never reads park records, review findings, rulings or rework notes.
- Machine-readable signals: `park.json` (`kind` enum in `factory-core/src/park.rs:19`), `usage.jsonl`, `events.jsonl`, board `task_index`.
- Prose-only signals: ledger rulings (`progress.md`), builder status (NEEDS_CONTEXT and DONE_WITH_CONCERNS are not persisted as fields), reviewer findings (tags `[blocker]` and `[minor]`), `checks.md`, rework notes (storage not found). No per-job record links plan quality to outcome.
- Injection points for lessons: the two command files that drive spec and plan writing, `crates/factory-engine/src/planlint.rs` (warns on missing fields, can host learned-rule checks), a repo-level context file like `.claude/factory/commit-context.md`, presets (`factory-core/src/preset.rs`), and the builder and reviewer prompts.
- Past fix commits with the shape a lessons loop would catch (inferred from commit messages, not tied to review findings): 8ec1063, ff1ef5d, dd24bbd, 5e6d502, 49b7d2a. The common pattern is input classes that no task's tests exercised.
- The job-history folders in the repo are empty, so real outcome data lives in `~/.factory/projects/*/state/jobs/`.

Candidate work:
- Write one machine-readable `outcome.json` per job (park kinds, rounds, findings by tag, rework count, tokens per task).
- A post-merge or post-park retro step that distils findings into a short `lessons.md` per project, capped in size.
- Load `lessons.md` in `/factory` plan authoring and in planlint.
- Decide a review gate so lessons are curated, not accumulated blindly.

Open questions: where does the lessons file live (repo `.claude/factory/` or the factory home), and who approves a lesson?

## Item 2: Agent Teams feasibility

Verdict: not feasible for the driver, and not currently used.
- The factory does not use Agent Teams. It uses subagents through the Agent tool: `BUILDER_TOOLS` (`specs.rs:19`) and `KB_TOOLS` (`kb.rs:17`). Lint tests forbid SendMessage (`crates/factory-cli/tests/agent_lint.rs`).
- Per the Claude Code docs, teams need `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` and work only in interactive sessions. In `claude -p`, a named subagent runs as an ordinary subagent. Teammates have their own context windows (docs cite up to about 7x tokens in plan mode), no per-team budget, no worktree isolation and no resume.
- Keep one `claude -p` per task in its own worktree. For fan-out inside a builder use subagents, bounded by `maxTurns` and `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`. The earlier variant B spike (controller plus subagents) is parked, see the memory note `factory-execution-variant-b-later`.
- Docs: https://code.claude.com/docs/en/agent-teams.md
